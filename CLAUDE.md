# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tasquel is a weekly checklist iOS app (iPhone + iPad) built with SwiftUI, targeting iOS 26.0. Bundle ID: `com.symonym.Tasquel`. No external dependencies — pure Apple frameworks.

Users organize tasks into categories within weekly views. Tasks support three modes (carry-over, repeating, one-time), sub-tasks, and automatic weekly rollover. Categories are saved as reusable templates.

## Build & Test Commands

```bash
# Build
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build

# Run unit tests (Swift Testing framework)
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test

# Run a single test
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -only-testing:TasquelTests/TasquelTests/testExample test
```

Simulator: iPhone 17 Pro (iOS 26.3). The minimum, iOS 26.0, is the final release (23A343, installed 2026-11-14), and Tasquel launches there. It replaced a beta runtime (23A5276e) that lacked a FoundationModels initializer the `@Generable` code links to, so the app died at launch on it (dyld "Symbol not found"). A crash like that means a beta runtime, not an app bug. Check narrow screens on an iPhone SE created on 26.3. Files added to the `Tasquel/` folder are auto-discovered by the build system (`PBXFileSystemSynchronizedRootGroup`).

### Data Models (`Models.swift`)

- **`TaskMode`** — `.carryOver` (rolls if incomplete), `.repeating` (every week), `.oneTime` (never carries)
- **`TaskType`** — `.checkbox`, `.goal` (target/progress/unit) or `.list` (items stored as sub-tasks; checks itself off; `isListFolded` saves its fold, `isFolded` is that for lists only). Type and mode are independent.
- **Expiration** — `ChecklistTask.expiresOn` (its last day, a `DayKey`), `expirySetOn` (for the ring) and `expiresWithWeek` (picked as a week); `isExpired(before:)`, `expiryTimeLeft(on:)`, `takeExpiry(from:)`.
- **Pins** — `Category.isPinned` and `ChecklistTask.isPinned` (up to `Category.maxPins`, 2); `Category.orderedTasks` lists pinned tasks first.
- **`SubTask`**, **`ChecklistTask`**, **`Category`** (name + SF Symbol + tasks)
- **`Week`** — container of categories, identified by `startDay` (a `DayKey`: Gregorian year-month-day, saved as `"yyyy-MM-dd"`), not by a moment, so time-zone changes can't duplicate weeks. `startDate` is computed (midnight in the current time zone) and still written for older builds; files without `startDay` get it from `startDate` in the current time zone on first load and are re-saved. `dismissedCarryOvers` / `dismissedRepeating` record tasks the user deleted from that week.
- **`GoalNumber`** — locale-aware goal amount parsing/formatting; goal values are capped at `GoalUnitKind.maxValue` (999,999)
- **`CategoryTemplate`** — saved category name+symbol for reuse
- **`AppearanceMode`** — `.system`, `.light`, `.dark`, `.retro`; **`RetroColor`** — retro phosphor palette

### Store (`ChecklistStore.swift`)

Single `@Observable` store owns all app state. `init(directory:defaults:now:calendar:)` defaults to the Documents folder, `UserDefaults.standard`, `Date()` and `Calendar.current`; **tests must pass a temp directory and a throwaway defaults suite** (`makeIsolatedStore()`) so they never touch real data, and a `TestClock` when they depend on today or the time zone. Past/current/future checks live on the store (`isPastWeek(_:)`, `isCurrentWeek(_:)`, `isFutureWeek(_:)`) so they use that clock. Week dates always use `Calendar.weekDates(in:)` (Gregorian, user's time zone), never `Calendar.current`, so non-Gregorian device calendars find the same weeks.

- **`checklist.json`** — array of `Week` objects (all task data)
- **`settings.json`** — templates, appearance mode, retro color, onboarding flag
- `UserDefaults` — `didMigrateStarters_v1`, `categoryEditTimes` (card sort), `matchAppIconToTheme`, `didSendComingSoonSurvey` (an old `userName` key may linger; nothing reads it). settings.json also holds calendar events on/off and the chosen calendars, `weekStartsOnSunday`, `categorySort` (a raw string), `offeredStarterNames` and `removedSavedCategoryNames`. A theme or retro color this version doesn't know reads as System / green (lenient `init(from:)` on `AppearanceMode` and `RetroColor`), so settings from a newer build never stop the app at the load-error screen.
- **Removed saved categories** are remembered in settings (`removedSavedCategoryNames`), so deleting a card with that name doesn't save it again.
- **The week start follows the saved weeks** (`inferWeekStartFromSavedWeeks`, on every load): weeks always move with the setting, so when the two disagree (no settings.json after Start Fresh, or a week-start change that saved one file but not the other) the most recent saved week's weekday wins, and the current week stays reachable.
- **Starter categories** are added to saved categories only on first launch; `offeredStarterNames` in settings remembers which were offered, so ones the user removes (even all of them) never come back. Onboarding doesn't choose categories; a new user starts with the starters.

Key behaviors:
- **Weekly rollover**: a week is built by rolling forward categories from the most recent saved prior week. Repeating tasks always carry (reset). Carry-over tasks carry only if incomplete. One-time tasks never carry. Category UUIDs change every week.
- **Future weeks are previews until edited**: only the current week is created by looking at it (`ensureWeekExists` at launch / navigation). Any other unsaved week is `previewWeek(for:)` (cached so IDs stay stable; rebuilt, it takes the last preview's IDs, and a saved later week's preview does for what sync adds to it) and `selectedWeek` returns it. Every mutation goes through `editableSelectedWeekIndex()`, which saves the preview first. Saved future weeks keep syncing with the week before (`syncWithPreviousWeek`): untouched carried copies (`carriedFrom`) follow or leave with their source (a task the user added or changed in its week has `isUserEdited` and is never followed, removed or adopted; a rename alone doesn't count: a renamed copy keeps its name, `hasOwnTitle`, and follows in everything else, leaving with its source like any copy, and renamed back to its source's name it follows renames again; the user's choice, 2026-11-12: "Bugs 1.0.2" this week, next week's copy renamed "Bugs 1.0.3", what's left of 1.0.2 still going to 1.0.3), missing ones are added unless dismissed, and missing repeating tasks are added unless in `dismissedRepeating`. When a saved week becomes current it gets one final full sync (follow/remove untouched copies, no categories re-added) and is marked `didFinalSync`, so later edits to the current week are never undone; a week that is in the future again (opened where it was already that week, Tokyo on a Sunday evening in New York, then back west) loses the mark and follows the week before again, getting its final sync once more when it's current (the 2026-11-15 review: a task finished this week stayed, unchecked, in next week). A saved week that came and went without the app being opened gets the final sync it missed (`finishSkippedWeeks`, oldest first) before any week is built or synced from it, so tasks finished since it was saved don't come back.
- **Load order** (`loadAndPrepare`, used by init, `retryLoadingData` and `setAsideUnreadableData`): settings → seed starter templates → weeks → week start from the saved weeks → `selectedDate` to the current week → keep This week only categories → prune edit times → ensure current week → starter migration → sync with the week before.
- **`selectedDate` is noon on the viewed week's fourth day** (`midweek`, set by `navigateToDate`, the week-start switch and loading), never a week's first midnight: a westward time-zone change moved that into the week before ("Past week · view only"). ContentView keeps the current week as a `DayKey` (`currentWeekStart`) to tell whether the viewed week was current when the day or time zone changes.
- **Dismissals follow the chain of copies** (`extendedDismissals`): a task deleted from a week stays deleted there as its source becomes a copy of a copy week by week (any source task whose `carriedFrom`/`repeatsFrom` links lead back to a dismissed task is dismissed too). A carried or repeating task already copied into another card of the week (renamed, with a new card taking the old name) isn't copied again. A repeating list's checks came with it, so they don't keep an otherwise untouched copy when its source goes. (The type/mode picker's Repeating hint says so by type, `modeHint`: "checks kept" for a list, "from zero" for a goal; "unchecked" read wrong to a tester whose grocery list came back checked.) Sync's own saves (`save(keepsUndo: true)`) don't end a delete's Undo. Picking a task's mode in the type/mode picker, even the one it has, brings it back: later saved weeks forget that it or a copy of it (found by their links, in saved weeks and previews) was deleted there (`undismissCopies`), so sync adds it again; the same mode isn't an edit (the user asked, 2026-11-12: a list carried into next week, its copy there renamed and then deleted, never came back however its mode was set; Help says how). Week-start changes forget preview IDs (`lastPreviews`), and a preview never takes a saved week's ID.
- **Load-failure safety**: if either JSON file fails to decode, `persistenceError` is set, all saves are blocked (so defaults never overwrite the file), and `ContentView` shows a retry screen with Start Fresh (`setAsideUnreadableData()` renames the bad file, never deletes it). Task decoding is lenient (missing fields and unknown enum values get defaults). Save failures set `saveError` (an alert, only for the first failure in a run of them) and `isSaveFailing` (a lasting "Changes aren't being saved" notice under the week bar); failures are tracked per file, so both clear only when both files have saved, and a successful save retries the other file. The load-error screen also links to Support.
- **One store per app**: `TasquelApp` owns the store and calendar service and passes them to `ContentView`, so iPad windows share them.
- **Past weeks are read-only**: `editableSelectedWeekIndex()` returns nil for them. A past week with no saved week on or before it is from before Tasquel was used and has no cards ("Nothing was planned this week"; `makeWeek` seeds only a current or future first week from Saved Categories, which also keeps deleted cards).

### UI Patterns

- **Orientation**: iPhone is portrait only; iPad supports all four (iPadOS 26 windows resize freely, so portrait-only can't be enforced there). Build settings `INFOPLIST_KEY_UISupportedInterfaceOrientations_*`.
- **Card grid** (`ScrollView`, not `List`): collapsed cards in rows of 2 (iPhone, or a compact-width iPad window), 3 (iPad portrait) or 4 (iPad landscape / wider than tall); an expanded card takes a full-width row, or in four columns half the width, in a lane it keeps while it's open (see `CategoryGridLayout`). Multiple cards can be open; expansion is tracked by `CategoryLayoutKey` (name + occurrence) since UUIDs change per week, so open cards persist across week navigation (in memory only). Within a week the grid's `ForEach` is keyed by category ID, so a renamed card stays the same view (a menu, sheet or field open in it survives); `reconcileCardKeys` moves open/editing/order keys when a category is renamed anywhere (Saved Categories too) and forgets deleted ones, all at once from the state as it was (`remapCardKeys`; one at a time, in a dictionary's order, deleting the first of two same-named cards could close the second). Opening a card that isn't first in its row moves it to the row's start only for show (`categoryDisplayOrder`): leaving Edit and sort changes re-lay out open cards (`reopenCards`), and a drag saves only the dragged card's move (`savedOrder`). Columns use the window's size (`WindowSizeReader`), which keyboards don't change; a new number of columns (an iPad turned or resized) lays the open cards out again as if opened in it (`columnsFollower`). The bottom bar ignores the keyboard's safe area, so behind a sheet's keyboard (iPad) it stays at the bottom. A list's Add Item field scrolls back into view after each add, as Add Task does (pasted lines left it far below the screen). In Seasonal, Settings, Help and Add Category take the season's accent, not system blue.
- **Bottom bar**: no bar of its own; Settings (glass circle, left), the week selector (glass capsule, center) and Edit/Done as text (glass capsule, right) float above the home indicator, each with its own Liquid Glass (`BarBackground`; Done is tinted green). The selector's middle button opens the calendar sheet: a plain calendar, or with calendar events on a green `calendar.and.person`. Retro keeps its bordered boxes instead of glass. Each side is as wide as the wider of Edit and Done (`editSideWidth`, measured from both words laid out hidden), the Settings side copying it, so the selector stays centered and its arrows get their full 44pt on every iPhone (sides sized for two buttons left them ~30pt on an SE). The words stop growing at xxxLarge (`editLabel`'s `.dynamicTypeSize`): at the largest sizes they squeezed the arrows to 28pt. Taps between the buttons reach the cards. The grid's bottom padding follows the row's measured height.
- **Edit mode (bottom bar)**: category management — the Add Category tile first, in the grid's top-left slot (at the end it was below the screen with ten cards; a button beside the hint was too small and close to a delete badge, the user, 2026-11-15; card drags go by measured frames, so the tile ahead of them is fine), delete badges, and a "Hold and drag a card to move it" hint; open cards collapse (and reopen when editing ends) and can't open meanwhile. A card's own edit button edits only that card's tasks (trash cans, renaming).   - **Dates:**
