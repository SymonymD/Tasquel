# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tasquel is a weekly checklist iOS app (iPhone + iPad) built with SwiftUI, targeting iOS 26.0. Bundle ID: `com.symonym.Tasquel`. No external dependencies — pure Apple frameworks.

Users organize tasks into categories within weekly views. Tasks support three modes (carry-over, repeating, one-time), sub-tasks, and automatic weekly rollover. Categories are saved as reusable templates.

## Build & Test Commands

```bash
# Build
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build

# Run unit tests (Swift Testing framework)
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test

# Run a single test
xcodebuild -project Tasquel.xcodeproj -scheme Tasquel -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -only-testing:TasquelTests/TasquelTests/testExample test
```

Simulator: iPhone 17 Pro (iOS 26.3). The installed iOS 26.0 runtime is a beta (23A5276e) without a FoundationModels initializer the `@Generable` code links to, so the app dies at launch there (dyld "Symbol not found"); real iOS 26.0 has it. Check narrow screens on an iPhone SE created on 26.3 instead, and the minimum on a final 26.0 runtime. Files added to the `Tasquel/` folder are auto-discovered by the build system (`PBXFileSystemSynchronizedRootGroup`).

### Data Models (`Models.swift`)

- **`TaskMode`** — `.carryOver` (rolls if incomplete), `.repeating` (every week), `.oneTime` (never carries)
- **`TaskType`** — `.checkbox`, `.goal` (target/progress/unit) or `.list` (items stored as sub-tasks; checks itself off). Type and mode are independent.
- **`SubTask`**, **`ChecklistTask`**, **`Category`** (name + SF Symbol + tasks)
- **`Week`** — container of categories, identified by `startDay` (a `DayKey`: Gregorian year-month-day, saved as `"yyyy-MM-dd"`), not by a moment, so time-zone changes can't duplicate weeks. `startDate` is computed (midnight in the current time zone) and still written for older builds; files without `startDay` get it from `startDate` in the current time zone on first load and are re-saved. `dismissedCarryOvers` / `dismissedRepeating` record tasks the user deleted from that week.
- **`GoalNumber`** — locale-aware goal amount parsing/formatting; goal values are capped at `GoalUnitKind.maxValue` (999,999)
- **`CategoryTemplate`** — saved category name+symbol for reuse
- **`AppearanceMode`** — `.system`, `.light`, `.dark`, `.retro`; **`RetroColor`** — retro phosphor palette

### Store (`ChecklistStore.swift`)

Single `@Observable` store owns all app state. `init(directory:defaults:now:calendar:)` defaults to the Documents folder, `UserDefaults.standard`, `Date()` and `Calendar.current`; **tests must pass a temp directory and a throwaway defaults suite** (`makeIsolatedStore()`) so they never touch real data, and a `TestClock` when they depend on today or the time zone. Past/current/future checks live on the store (`isPastWeek(_:)`, `isCurrentWeek(_:)`, `isFutureWeek(_:)`) so they use that clock. Week dates always use `Calendar.weekDates(in:)` (Gregorian, user's time zone), never `Calendar.current`, so non-Gregorian device calendars find the same weeks.

- **`checklist.json`** — array of `Week` objects (all task data)
- **`settings.json`** — templates, appearance mode, retro color, onboarding flag
- `UserDefaults` — `didMigrateStarters_v1` (an old `userName` key may linger; nothing reads it)
- **Removed saved categories** are remembered in settings (`removedSavedCategoryNames`), so deleting a card with that name doesn't save it again.
- **Week start without settings.json** (Start Fresh after it couldn't be read) is inferred from the most recent saved week's weekday, so Sunday weeks stay reachable.
- **Starter categories** are added to saved categories only on first launch; `offeredStarterNames` in settings remembers which were offered, so ones the user removes (even all of them) never come back. Onboarding doesn't choose categories; a new user starts with the starters.

Key behaviors:
- **Weekly rollover**: a week is built by rolling forward categories from the most recent saved prior week. Repeating tasks always carry (reset). Carry-over tasks carry only if incomplete. One-time tasks never carry. Category UUIDs change every week.
- **Future weeks are previews until edited**: only the current week is created by looking at it (`ensureWeekExists` at launch / navigation). Any other unsaved week is `previewWeek(for:)` (cached so IDs stay stable) and `selectedWeek` returns it. Every mutation goes through `editableSelectedWeekIndex()`, which saves the preview first. Saved future weeks keep syncing with the week before (`syncWithPreviousWeek`): untouched carried copies (`carriedFrom`) follow or leave with their source (a task the user added or changed in its week has `isUserEdited` and is never followed, removed or adopted), missing ones are added unless dismissed, and missing repeating tasks are added unless in `dismissedRepeating`. When a saved week becomes current it gets one final full sync (follow/remove untouched copies, no categories re-added) and is marked `didFinalSync`, so later edits to the current week are never undone. A saved week that came and went without the app being opened gets the final sync it missed (`finishSkippedWeeks`, oldest first) before any week is built or synced from it, so tasks finished since it was saved don't come back.
- **Load order** (`loadAndPrepare`, used by init and `retryLoadingData`): settings → seed starter templates → weeks → ensure current week → starter migration.
- **Load-failure safety**: if either JSON file fails to decode, `persistenceError` is set, all saves are blocked (so defaults never overwrite the file), and `ContentView` shows a retry screen with Start Fresh (`setAsideUnreadableData()` renames the bad file, never deletes it). Task decoding is lenient (missing fields and unknown enum values get defaults). Save failures set `saveError` (an alert, only for the first failure in a run of them) and `isSaveFailing` (a lasting "Changes aren't being saved" notice under the week bar); failures are tracked per file, so both clear only when both files have saved, and a successful save retries the other file. The load-error screen also links to Support.
- **One store per app**: `TasquelApp` owns the store and calendar service and passes them to `ContentView`, so iPad windows share them.
- **Past weeks are read-only**: `editableSelectedWeekIndex()` returns nil for them.

### UI Patterns

- **Orientation**: iPhone is portrait only; iPad supports all four (iPadOS 26 windows resize freely, so portrait-only can't be enforced there). Build settings `INFOPLIST_KEY_UISupportedInterfaceOrientations_*`.
- **Card grid** (`ScrollView`, not `List`): collapsed cards in rows of 2 (iPhone, or a compact-width iPad window), 3 (iPad portrait) or 4 (iPad landscape / wider than tall); an expanded card takes a full-width row. Multiple cards can be open; expansion is tracked by `CategoryLayoutKey` (name + occurrence) since UUIDs change per week, so open cards persist across week navigation (in memory only). Within a week the grid's `ForEach` is keyed by category ID, so a renamed card stays the same view (a menu, sheet or field open in it survives); `reconcileCardKeys` moves open/editing/order keys when a category is renamed anywhere (Saved Categories too) and forgets deleted ones. Opening a card that isn't first in its row moves it to the row's start only for show (`categoryDisplayOrder`): leaving Edit and sort changes re-lay out open cards (`reopenCards`), and a drag saves only the dragged card's move (`savedOrder`). Columns use the window's size (`WindowSizeReader`), which keyboards don't change.
- **Bottom bar**: no bar of its own; Settings (glass circle, left), the week selector (glass capsule, center) and Edit/Done as text (glass capsule, right) float above the home indicator, each with its own Liquid Glass (`BarBackground`; Done is tinted green). The selector's middle button opens the calendar sheet: a plain calendar, or with calendar events on a green `calendar.and.person`. Retro keeps its bordered boxes instead of glass. Taps between the buttons reach the cards. The grid's bottom padding follows the row's measured height.
- **Edit mode (bottom bar)**: category management — add-category card and delete badges, with a "Hold and drag a card to move it" hint; open cards collapse (and reopen when editing ends) and can't open meanwhile. A card's own edit button edits only that card's tasks (trash cans, renaming). Deleting a category removes it from the viewed week and all later weeks (earlier weeks keep it; a future week records it in `dismissedCategories` so syncing doesn't add it back) and keeps its saved template.
- **Card sort** (Settings ▸ Categories ▸ Sort Cards, `store.categorySort`): Manual (hold and drag), Recently Edited First, or Least Recently Edited First (never-edited cards count as oldest: last, or first). Edit times are per category name in UserDefaults (`categoryEditTimes`, set by `noteEdit` in every task mutation and by adding a category; renames carry them; names no longer used are pruned at launch). The setting is stored as a raw string, so an unknown value reads as Manual. ContentView applies a snapshot (`sortedNames`) refreshed only on launch, return from the background (not Notification Center), week change, leaving Edit, setting change, or when every card is closed (a renamed card keeps its place), so cards never jump while being used; card dragging is off unless Manual.
- **Card hold-to-move** uses UIKit's `UILongPressGestureRecognizer` (`CardHoldRecognizer`, 0.5s), not a SwiftUI LongPress-then-Drag: that drag claimed every touch on a card, so a screen full of cards couldn't scroll.
- **Performance**: per-frame values (card frames, pull distance) are kept out of ContentView's observed state (`CardFrameStore`, the `PullToCloseAll` modifier), since each change re-evaluates the whole screen.
- **Goal row**: the goal's sliders button (`slider.horizontal.3`; the pencil icons are other screens' edit buttons), its bar (`GoalBarStyle`, 8pt) and the amount on one line (`.goalBar` alignment), with the − and + steps centered under the bar, together about a third of its width (`GoalStepsLayout`; a label that needs more room gets it). The sliders open the editor (Target and Step; no Progress field: progress only moves by steps, and a switch to or from Time carries it over); tapping it again closes the editor without saving. Each step's tap area is 44pt tall and reaches outward and into half the gap (`stepTapArea`), since 44pt squares around two small pills overlapped. With no progress + is alone, centered; the first tap nudges it over as − comes in (− only as wide as it needs, so + moves less than half its width, and − ignores taps for 0.4s after it appears so a quick second tap meant for + can't undo). **Goal quick steps**: the step is the task's `goalStep` (the editor's Step; copied to carried and repeating copies) or, when unset, 1 for counts and for time a step that scales with the target (≤20m: 5m, ≤1h: 10m, ≤3h: 15m, else 30m). − shows once there's progress (also after the goal is met) and never goes below zero; + stays after the target is met, so a goal can be exceeded (up to `GoalUnitKind.maxValue`). + keeps its place while hidden at the maximum (`goalSteps`), so nothing slides under a finger between quick taps; at accessibility sizes the amount goes under the bar. Return in a goal field saves like Done (iPad and hardware keyboards have Return); an amount over 999,999 or a zero target/step says why under the field (`GoalAmountInput.problem`). Smart Add drops goal amounts and list items a model invents (`TaskTextHints.dropInvented`) and corrects close typos in the title and unit with `UITextChecker` (`AppleIntelligenceTaskParser.fixingTypos`; words the user capitalised are kept).
- **Pull to close all**: pulling the grid down past its top by `PullToCloseAll.distance` (90pt) and letting go closes every open card. It counts only while the finger is on the grid (`onScrollPhaseChange` `.interacting`), so a fast scroll's bounce at the top never triggers it; a hint ("Pull / Release to close all") and a light haptic show when it's armed.
- **Week paging**: last/this/next week are laid side by side (`PagerTrack`); drag offset lives in `WeekPagerState` so dragging doesn't rebuild pages.
- **Header / bottom bar**: the header shows the viewed week ("Week of …", 5% under `.title2`) in a frosted header bar (`weekHeader`, `.thinMaterial` up behind the status bar, the cards scrolling under it through `safeAreaInset`; solid with a rule in Retro), between the Tasquel mark (30pt; `TasquelMark`, a template SVG of the app icon's ring and t placed as in `AppIcon.icon`; `TasquelMarkRetro`, the t in brackets, in Retro; back to this week) and Open/Close All, with the day strip under it; the bottom bar shows Settings, the week selector, and Edit. The selector is hidden with the bar while the keyboard is up; swiping still changes week.
- **Calendar events**: the calendar sheet's Events side shows the viewed week's events (`CalendarEventsList`), fed by `CalendarService` (loaded ahead by the selector's calendar button); a sideways swipe on it pages weeks with the cards behind (left for next): the next or previous week's events come in beside the finger, and on release both slide on the same spring, the events landing on the week the store moved to (`latestEventsWeek`: an animation's completion sees the sheet's props as they were). The page width is measured but never fed back into the content's width (measured while the sheet was still presenting, the list stayed narrow). Once a drag is clearly sideways the events are disabled for that touch, so a swipe that starts on an event doesn't open Calendar (VoiceOver: Next week / Previous week actions); tapping an event opens the Calendar app at its date (no long-press gesture on events: it stopped the list scrolling). Calendars reload after a real trip away, not after Control Center or the icon alert. Event data is never persisted.
- **Week start**: Sunday or Monday (Settings ▸ Week). Use `store.startOfWeek(containing:)`, never a hard-coded Monday; changing the setting moves every saved week by the same number of days so the week containing today stays current: one day, or six on a Sunday.
- **Destructive actions**: deleting a task or sub-task doesn't ask; it can be undone for 5s from a "Deleted … · Undo" message (`store.lastDelete` / `undoLastDelete()`, a snapshot of the weeks from just before; any other save ends it). Deleting a category or template and goal → checkbox go through `confirmationDialog` (a category delete can be undone too). With VoiceOver on, the Undo message stays until the next change; the week title and the cards have an "Undo delete" action. Undo from another week goes back to the week of the delete (`UndoableDelete.week`). Taking back a Smart Add uses `deleteTask(undoable: false)` (no Undo message). Any change to saved categories ends the undo. Removing a saved category uses the shared `savedCategoryRemoval` dialog in both Settings and Add Category.
- **Add task row**: a card's Add task field waits behind a larger + (`PlusOpener`, scaled so it shrinks smoothly; a list's Add item field too, and a sub-task's field wipes open from the task's +, both with 4pt between + and field and the fill ending at the type/mode button's right edge). Tapping it wipes the field open from the + (`.revealFromLeading`, 0.2s ease-out) and gives it the keyboard when the wipe ends: focusing during it held the main thread while the keyboard loaded, and the wipe froze, then jumped. With the keyboard gone and nothing typed it folds back to the + (`closeFieldIfIdle`; it stays while there's text, Smart Add is working or its options are open). A hidden stand-in keeps the closed row as tall as the open one. VoiceOver hears the + as "Add task" only while closed: a clear 44pt button over the image exists only then (not `accessibilityHidden`, which an open card undoes, nor `accessibilityRepresentation`, whose stand-in took the wrong frame: half the row, or a whole list task). UI tests reach the field through `app.addTaskField` (TasquelUITests/AddTaskField.swift), which taps the + first.
- **Keyboard Done**: while the keyboard is up the bottom bar becomes a small round keyboard-down button at the right (VoiceOver: "Done"); it bumps `store.keyboardDoneRequests` before closing the keyboard; rows with a typed but unadded task, sub-task or goal amount save it then (number pads have no Return key). The Add task, sub-task and item fields are multi-line (`axis: .vertical`): Return types a line break, which adds what's before it (`submitTyped`) without ending editing, so the keyboard and bar don't bounce; Return in an empty field closes the keyboard. The bar makes way only for a keyboard taller than 100pt (not a hardware keyboard's shortcuts bar). A card's own edit mode ends when the week changes, and starting it saves a typed sub-task. On iPad a task's type/mode button (new or existing task) closes the keyboard first and opens the picker once it's down: with the keyboard up the picker went partly off the screen.
- **Keyboards in sheets**: while a sheet ContentView presents is up (`isSheetPresented`), ContentView ignores keyboard-show notifications and stops measuring the home-indicator inset (the bar's height is still measured: Settings can change it). A keyboard in a sheet over a sheet (Choose Emoji… in Add Category or Saved Categories, Settings ▸ New Saved Category) lifts the main screen's safe area to ~380pt; the bar, padded by that inset, chased it in a layout loop that froze the app (build 1). Focus a field once when it opens (`onChange`), never in `onAppear` of a List row: the List rebuilds rows when a keyboard moves the sheet, and the field took the keyboard back from the emoji picker. Choose Emoji… shows its picker from the sheet's root (`.emojiPickerHost()` on Add Category, Saved Categories and the saved-category editor), not from the icon menu: the menu sits in a List row, which the List removes and rebuilds while a sheet opens over it, and a picker shown from the row was rebuilt with it, each new emoji field taking the keyboard down and up again. The menu also lets go of the keyboard before the picker opens, or iOS hands it back to the name field as the picker closes and takes it away again a moment later. A UI test can't see either bounce (XCUITest waits for animations to settle before looking). `EmojiPickerUITests` covers these flows.
- **Past weeks** show "Past week · view only" under the week bar, with dimmed checkboxes.
- **Add Category**: a "This week only" toggle (off = every week) applies to whatever is added next; no second dialog. A category added for this week only is kept in Saved Categories too (ones from before are saved at launch, `saveThisWeekOnlyCategories`, unless removed there).
- **This week only on a card**: a card's own edit mode has a This week only switch (`ThisWeekOnlyToggle`, `store.setCategoryThisWeekOnly`) where the Add task row is outside edit mode, so no row moves as editing starts (with it under the card's name, the rows slid down and a tap meant for a delete button opened a sub-task field). On: its carry-over and repeating tasks become one-time, and later weeks lose the category, keeping only tasks the user added or changed there. Off: it comes back next week. Adding a carry-over or repeating task to such a card, or changing a task to one, turns it off (`keepCategory`); the picker's hint says so.
- **Reordering tasks**: in a card's edit mode each task has a drag handle (`.draggable` / `.dropDestination` of a `TaskDragItem`, raw data so text fields don't paste it; only within the same card); VoiceOver gets Move Up / Move Down. `store.moveTask` records the category in the week's `userOrderedCategories`, so syncing with the week before leaves that order alone.
- **Header**: `Week.displayTitle` is "Week of Oct 5" in the user's locale, with the year only when it isn't this year.
- **Haptics**: light tap on ticking a task, selection on sub-tasks, success on finishing a goal or a whole card (keyed by category ID so paging weeks is silent). Closed cards with no tasks say "No tasks yet · Tap to add"; a ring is grey until something is done; done tasks are struck through.
- **Tasks**: checking a task with sub-tasks (or a list) checks them all; unchecking puts back the checks from before (cleared if there were none). Edits that change nothing (same name, same mode) don't mark a task `isUserEdited`. Typed but unadded tasks and sub-tasks are added however the keyboard closes; closing a card dismisses the keyboard first. Cards lift for dragging after a 0.5s hold. Tapping a task's or sub-task's name renames it. An open card also closes from a tap on its icon or name.
- **Store changes from async code**: never change the store from a `Task` after an `await` (or a dispatched block) inside `withAnimation`. SwiftUI then flushes its pending updates during the change, redrawing views from the data as it was before, and a screen redrawn that way misses the change (Smart Add's task was added but its card showed none). Hand the result to the view as `@State` and change the store in `onChange`, during SwiftUI's own update like a tap (`AddTaskRowCard.smartAddOutcome`). The Reduce Motion week change in `ContentView` still calls `navigateToDate` from `asyncAfter`.
- **No swipe actions** (they require `List`); use edit-mode controls (no long-press menus on cards or tasks).
- **Text fields in cards** use `.cardField(theme, rc:)` (Theme.swift): a soft fill with 8pt rounded corners (2pt in retro); `outset: true` draws the fill around the text so a name and its rename field line up.
- **Retro theme**: every view branches on `Theme.isRetro(theme)` for monospaced fonts/terminal styling.
- **Accessibility**: small icon buttons get a 44pt hit area with `.touchTarget()` inside the label (no layout change). Retro text colors (bright/dim/faint, `retroRed`) keep 4.5:1 on a retro card; `glow` is only for the card shadow. Done/not done never relies on color alone (filled vs. outline). At accessibility text sizes every card takes a full row (`usesSingleColumn`), the type/mode picker is one column, the goal editor stacks, and row icons stop growing. Reduce Motion turns off the card spring (`cardAnimation`), sliding transitions and the events panel's bounce. An open card is `.accessibilityHidden(false)`, which re-exposes children hidden with `.accessibilityHidden(true)`: hide decorative views inside cards with `.hiddenFromVoiceOver()` instead. A checkmark icon gives a button the Selected trait: remove it (`.accessibilityRemoveTraits(.isSelected)`) where nothing is selected. Week titles and open card names are headings; Retro text has plain-language labels. `CategoryCard` sets `isCardOpen` for its contents, so a hidden field never takes the keyboard.

## Swift Configuration

- Default actor isolation: `MainActor`
- Approachable Concurrency enabled

## Testing Launch Arguments

- Debug builds only.
- `-isolatedData`: the app uses throwaway storage (never the simulator's real data). Fresh data shows onboarding first.
- `-fakeCalendar`: sample calendar events instead of EventKit.
- `-smartAddRules`: Smart Add without a model (the rules it applies after the model, with a 2s pause), so it runs in a simulator (`SmartAddParser`, `RulesOnlyTaskParser`).
- `-demoData`: throwaway storage, no onboarding, and a current week filled with sample tasks (`DemoData.swift`), plus a fuller set of fake events; `-demoAppearance <system|light|dark|retro>` picks the theme, `-demoFirstCard <name>` puts that card first (so it opens at the top), and `-demoToday yyyy-MM-dd` makes that day today (the store's clock, which the day strip and events list read through `store.currentDate`). For App Store screenshots.

## App Store Screenshots

`scripts/app-store-screenshots.sh [iphone|ipad]` boots an iPhone 17 Pro Max and an iPad Pro 13" (M5) simulator (iOS 26.3), sets a 9:41 status bar (dated, for iPad's date), makes the demo's today the Wednesday of this week (`DEMO_TODAY` overrides), so the day strip shows past days, today and days to come, and runs `ScreenshotTests` (skipped in normal test runs), which steps through the screens with `-demoData` and has the script take each picture with `xcrun simctl io … screenshot`. On iPad it first sets Settings ▸ Multitasking & Gestures ▸ Full Screen Apps (windowed apps show a resize handle). Output: `screenshots/iphone/` (1320×2868) and `screenshots/ipad/` (2064×2752); the script checks the sizes. The seven shots: week, Smart Add (`-smartAddRules`), a card open, the type and mode picker in Dark, calendar events in Dark under an open card of goals, Retro, Dark. `python3 screenshots/appstore/make_appstore_images.py screenshots screenshots/appstore` (from the project folder) frames them with a headline and subhead for App Store Connect (captions in its `SHOTS`); it needs Pillow and Inter Display (`extras/otf` in the Inter release zip; `INTER_DIR` points to it).
